## Working copy location

Keep the checkout on the WSL ext4 filesystem (`~/projects/serverless/diet-tracker`) rather than
under `/mnt/c`. WSL reaches Windows drives through a file-sharing protocol that makes every file
open a round trip to the Windows side, and the development loop is built from the operations that
open the most files: interpreter startup, test collection, bundling. Importing boto3 from a
virtualenv costs 5.0s under `/mnt/c` against 0.30s on ext4, and collecting the backend test suite
14.5s against 0.9s.

Reading the files from Windows through `\\wsl$\` pays the same penalty in the other direction, so
a Windows-side editor relocates the cost rather than removing it.

`.venv` and `frontend/node_modules` record absolute paths in their scripts and metadata, so each
checkout builds its own instead of receiving a copy.

## Frontend

```sh
cd frontend && npm install && npm run dev
```

The dev server runs on port 8000 — the Cognito callback URL registered for local development.
`npm test` runs the Vitest suite.

Runtime configuration lives in `frontend/public/config.js`, generated by `lib/app-config.sh`,
which `deploy.sh` runs after every backend deploy; for a manual setup, copy
`frontend/config.example.js` there.

`frontend/public/demo.html` is the walkthrough linked from the README, published beside the app at
`/demo.html`. It is self-contained rather than part of the bundle: it carries its own copy of the
screen and a snapshot of the questionnaire and recorded history matched to each other, because its
narration names specific carb grades and scores.

## Configuration

`config/app.json` is read by both runtimes — the Lambda package carries it, `deploy.sh --frontend`
publishes it at the site origin root, and the Vite dev server serves it from the same source file.
Every edit to it needs a `deploy.sh --frontend` run: the Lambdas read the copy inside their package,
so a frontend publish alone changes only what the browser reads. The treat-day weekday and the
morning hour also reach the EventBridge schedules through that deploy — the weekday drives the day
the weekly recap goes out on, and the hour the daily morning job that sends the weigh-in reminder on
the treat day and queues the debrief of a heavy yesterday.

## Backend tests

`scripts/test.sh` runs `bash -n` on every script and then the backend pytest suite; it creates
`.venv` at the repo root on its first run. The GitHub Actions workflow `.github/workflows/ci.yml`
runs it on Python 3.13 and, beside it, `npm ci`, `npm test` and `npm run build` on Node 22.

## Deployment scripts (`scripts/`)

Install the AWS CLI, `jq`, `git`, `npm` and `python3` with its `venv` module (`python3-venv` on
Debian), each on `PATH`; `deploy.sh` stops naming the first one missing, and `test.sh` stops when it
cannot create `.venv` with pip in it. `./scripts/init-env.sh` creates the gitignored
`aws-config.sh`, `secrets.sh` and `params.sh` under `scripts/lib/` from their `.example` files; fill
them in before running any other script; each setting's comment says what it holds and whether it is
required. `lib/stack-params.sh` lists every parameter the stack pair is deployed with.

No script takes an environment argument. The git branch selects the stack pair every script
acts on: `main` targets `diet-tracker` with `diet-tracker-cognito`, any other branch
`diet-tracker-fb` with `diet-tracker-fb-cognito`, a fully isolated pair with its own Cognito
domain; an exported `STACK_NAME` wins.

Sign-in and mail depend on settings outside this repo, which must exist first. `SES_SENDER` in
`params.sh` must be an identity SES has verified, since every mail goes out from it. The Google
OAuth client of `secrets.sh` must list among its authorized redirect URIs the address
`./scripts/aws-helper.sh --redirect-uri` prints for the branch
([Setting up Google](sign-in.md#setting-up-google)).

- [`deploy.sh`](../scripts/deploy.sh) — packages and deploys both CloudFormation stacks
  (application and Cognito). `--frontend` also publishes the frontend; `--frontend-only`
  publishes the frontend alone. Both write `frontend/public/config.js` for the branch's stack
  pair first, through [`lib/app-config.sh`](../scripts/lib/app-config.sh).
- [`aws-helper.sh`](../scripts/aws-helper.sh) — AWS operations on the stack pair, the same file
  in every AWS repo: function logs, log retention, and `--delete-stack --empty` to empty the
  frontend bucket and tear the pair down. This repo's own options are in
  [`lib/aws-helper-app.sh`](../scripts/lib/aws-helper-app.sh): `--stack-logs` for a function of
  any stack, including the answering service's, `--set-rag-key` to store the answering
  service's API key in SSM, and `--emails` for one user's outgoing mail
  ([`lib/emails-helper.sh`](../scripts/lib/emails-helper.sh)): shows a message as undelivered,
  previews or sends the weekly recap or the morning debrief, and asks SES to mail an address its
  verification request again. `--help` prints both headers.
- [`test.sh`](../scripts/test.sh) — the quality gate, above.
- [`tools/`](../scripts/tools/README.md) — hands-on tools for one user's data: reset to a
  first sign-in, clone into a feature branch's stacks or fictive accounts, and a read-only dump
  that seeds `frontend/public/demo.html`.

`scripts/lib/app-env.sh` holds what the scripts share: the `--help` printer, the settings-file
loaders, which refuse a file git tracks, and the branch's stack selection.

## Telegram (optional)

Store a bot token at SSM parameter `/diet-tracker/telegram/bot-token`, plus a per-user chat-id map
at `/diet-tracker/telegram/chat-map`. While the token parameter is absent, the reminders and the
weekly recap go by email only.
